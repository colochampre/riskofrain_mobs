# Carried items display

Objective: show above each mob the Risk of Rain items it carries (from the mob item pickup feature), as item icons with a count, so players can see which mobs are worth hunting.
Branch: `1.20.1-carried-items-display` from `1.20.1-mob-item-pickup` (`a404e64`, PR #16 open); retarget to `1.20.1` once #16 is merged. Delivery: ask-on-risk. Push, PR and merge are the user's.
Test runner: none in the project. Checks are `./gradlew build`, dedicated servers stopped through rcon (no client classes loaded on the server), and the user's in-game test on Fabric and Forge.

## Specs

User request (2026-11-14): "se puede mostrar de alguna forma los items que tienen actualmente los mobs que los hayan recogido. Por ejemplo encima de su cabeza, así como los drones muestran como nombre el precio cuando no estan domesticados. Se puede mostrar el icono del item que tienen, y en caso de tener multiples de un tipo, con (item)x2 x3 x4... segun lo que tengan"

- S1: The six mobs that can carry items render a row of item icons above their head, one icon per distinct item, in the order the items were first found in the inventory. An item with a total count above 1 shows `x<count>` next to its icon (`x2`, `x3`, ...). The count is the total across stacks of that item.
- S2: Not through the custom name: names are text only in 1.20.1 and a name tag must keep working. Rendering is a client-only render layer or renderer hook, never loaded on a dedicated server.
- S3: The client learns what a mob carries through synced entity data: a compact summary (item id and total count per distinct item), updated on the server only when the inventory changes, not every tick. Nothing is synced for an empty inventory beyond the empty summary.
- S4: "Probamos con siempre dentro de cierta distancia, configurable". The row is visible whenever the mob is within the configured distance of the camera, not only when looked at. Not shown for an invisible mob, or when the HUD is hidden (F1).
- S5: "se puede volver a ponerles un nametag, y en ese caso, de tener items, estarían ambos presentes". When the mob's name would render (vanilla `shouldShowName`, which also covers the untamed drone price), the row is drawn above the name, so they never overlap.
- S6: "Probemos con 4 por fila. Luego del test te digo si prefiero más o menos". More than 4 distinct items wrap to another row, rows centered; rows face the camera like a name tag. Keep the per-row count in one constant so it is easy to change after the test.
- S7: Config entries in the existing "Item pickup" section: show carried items (true) and display distance in blocks (16, bounded 1 to 64), translated in en_us, es_es, es_mx and zh_cn. Both are read by the client only.

## Log

- L1 (2026-11-14), user chose "always within a configurable distance" over "only when aimed at". Drone price uses `setCustomName` (`AbstractDroneEntity.java:374`), text only, so icons need their own render.
- L2 (2026-11-14): T1-T3 done, `./gradlew build` passes. Sync: each of the five classes (Beetle, Lemurian, Stone Golem, Wisp, `AbstractDroneEntity`, which covers the Gunner Drone and Turret) defines its own `DATA_CARRIED_ITEMS` (`EntityDataSerializers.COMPOUND_TAG`, `SynchedEntityData.defineId` called from the entity itself: a first version went through an `ItemPickup` helper and Forge logged "defineId called for ... from class ItemPickup" warnings, vanilla checks the caller), registers it with `registerCarriedItems`, and builds its container with `ItemPickup.createInventory(this, accessor)`. That adds a `ContainerListener` that, on the server, writes `{Items: [{id, Count}]}` (total per distinct item, first-seen slot order; empty tag when nothing is carried). `SimpleContainer` calls `setChanged` from `addItem`, `setItem`, `removeItem` and `clearContent`, so pickup, load, overflow and drop-all are all covered with no per-tick work, and `SynchedEntityData.set` skips the packet when the new tag equals the old one, so the repeated refreshes while loading cost nothing on the wire. The client reads it through the `CarriedItemsSource` interface. Render: `client/renderer/CarriedItemsRenderer.render(...)`, called after `super.render` from the six renderers (those with a model scale call it after `popPose` and pass the scale), so it is client-only by construction: the renderers were already client classes loaded only through the client entrypoints, which register them. Parsing is cached per entity id and invalidated by tag identity (the client gets a new tag instance per update). Name tag offset: vanilla anchors the name at `getNameTagOffsetY()` (bbHeight + 0.5) and draws it hanging about 0.225 below that, so when `shouldShowName` is true the rows start at `getNameTagOffsetY() * renderScale + 0.05`, otherwise at `bbHeight * renderScale + 0.2`. Rows grow upward, 0.45 per row, 4 per row in `ITEMS_PER_ROW`. Decisions where the spec was silent: icons use `ItemDisplayContext.GUI` at 0.4 blocks, full-bright, text drawn as a vanilla name tag (see-through faint pass plus solid pass); an item id that no longer exists in the registry is skipped; the two config entries have no tooltips, as their siblings have none; the `CarriedItemsSource` interface lives in `utils/` (no client types). Billboard: after `cameraOrientation` a 180 degree turn around Y keeps +x to the viewer's right and the front of the icons toward the camera (vanilla name tags use a negative x scale instead, which would mirror a model). Risk for T5: the icons are drawn through the entity buffer in world lighting, so shading of flat items and the mirror orientation are only verifiable in game.
- L3 (2026-11-14): T4 done on Fabric and Forge, dedicated server stopped through rcon (`:fabric:runServer`, `:forge:runServer`, riskofrain_items 2.0.0 in `<platform>/libs`), on `0ff5c1b`. Both: `Done (`, `Stopping server`, `All dimensions are saved`, no ClassNotFound or client-class errors, no riskofrain exceptions or warnings (only the known "No data fixer registered" lines on Fabric). A Beetle summoned with `Inventory` of 2 items (`riskofrain_mobs:beetle_entity`, the id has the `_entity` suffix) keeps both in `data get entity` and is killed without any server error.
